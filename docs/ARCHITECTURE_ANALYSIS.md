# 慧根堂多租户数字人短视频平台 — 功能模块架构分析与差异化方案

> 基于现有代码库（hgt-commercial Laravel 11 + 8500 Python 微服务 + HEYGEM 容器）的深度审计，2026-08-02

---

## 一、模块拆分与前后依赖关系

### 1.1 五阶段分层模型

当前平台按**数据依赖方向**自然形成 5 个阶段，每个阶段的输出是下一阶段的输入：

```
┌─────────────────────────────────────────────────────┐
│ Phase 0 租户入驻                                     │
│   注册/登录 → Tenant + User 行创建                   │
│   ↓ 强依赖（粗线）                                    │
├─────────────────────────────────────────────────────┤
│ Phase 1 克隆（出片硬性前置条件）                       │
│   P1 形象克隆 → ModelAsset 表（静音模特视频）         │
│   P2 声音克隆 → TenantVoice 表（voice_id）           │
│   P6 封面素材 → CoverAsset 表（预设+自上传）          │
│   ↓ 强依赖                                            │
├─────────────────────────────────────────────────────┤
│ Phase 2 内容创作                                      │
│   P5 智能选题 → 文本稿                               │
│   智能二创 → 改写稿（三段式+违禁词清洗）              │
│   智能质检 → QcReport（文本QC + 视频技术QC）         │
│   人工审核 → VideoJob.publish_status                 │
│   ↓ 强依赖                                            │
├─────────────────────────────────────────────────────┤
│ Phase 3 视频出片（双模式共用字幕引擎）                  │
│   scroll 模式：幕后音不出镜（滚动字幕卡）              │
│   avatar 模式：数字人出镜（HEYGEM 嘴型对齐）          │
│   P4 字幕参数调试：字号/行数/描边/位置（双模式共享）    │
│   ↓ 数据流                                            │
├─────────────────────────────────────────────────────┤
│ Phase 4 分发与数据                                    │
│   批量外发 → PublishRecord                            │
│   数据指标录入 → MetricDaily                          │
│   数据复盘看板 → 聚合分析                              │
│   计费配额 → Tenant.quota_monthly 扣减               │
└─────────────────────────────────────────────────────┘
```

### 1.2 克隆作为前置条件的强制机制

当前代码中，**形象克隆和声音克隆尚未被强制为出片的前置门禁**——scroll/avatar 出片页可以直接提交，即使该租户从未上传过模特或克隆过声音。这是因为：

- `VideoController::generate()` 校验了 `tenant_id`、`duration`、`concurrency`，但**未校验** `ModelAsset` 或 `TenantVoice` 是否存在
- scroll 模式不需要模特（幕后音不出镜），但需要声音；avatar 模式两者都需要

**建议加强的前置校验逻辑**：

| 出片模式 | 必须具备的前置条件 | 当前状态 | 建议 |
|---|---|---|---|
| **scroll**（字幕卡） | 至少 1 条 TenantVoice（男声或女声） | ❌ 未校验 | 加 `TenantVoice::forTenant($tid)->exists()` 否则 422 |
| **avatar**（数字人出镜） | ≥1 条 ModelAsset（已 QC 通过）+ 男声 voice_id + 女声 voice_id | ❌ 未校验 | 三项全检，缺一不可 |

这样做的业务意义：**防止租户跳过克隆直接试用出片**，确保平台"先克隆、后生产"的商业闭环。

### 1.3 封面素材的定位

封面采用**通用模板 + 租户自上传双来源**模式（P6 已落地）：
- 平台预设 80 张（8 分类 ×10 张），`is_preset=true`，所有租户可读可用
- 封面**不烧进视频**（仅 VideoJob 引用 + 发布元数据），因此归属模型宽松
- 出片时可选"不使用封面"，非强依赖

**结论：封面是弱依赖（可选），不应作为出片前置条件。**

## 二、字幕与音频处理拆分评估

### 2.1 当前三种形式的本质差异

| 维度 | scroll（滚动字幕卡） | avatar（数字人出镜） | 共享部分 |
|---|---|---|---|
| **视觉输出** | 竖屏纯色背景 + PIL 逐帧绘制字幕 | HEYGEM 容器嘴型驱动 + 烧字幕拼片头 | — |
| **音频来源** | CosyVoice TTS（单声/双声） | CosyVoice TTS（按性别选声线） | 同一套 `tts_one()` + EMOTION_PROSODY |
| **字幕引擎** | `make_scroll_video.py`（卡拉OK高亮+历史淡出+未读暗显） | `finalize_v2_pil.py`（烧 ASS 字幕到视频帧） | 字体(SimHei)/描边/颜色参数一致 |
| **输入格式** | 对话/独白/改写稿均可 | 必须 女:/男: 格式对话（独白降级为男声） | — |
| **渲染耗时** | ~5-8 min（TTS 主导） | ~8-15 min（HEYGEM 嘴型 + TTS + ffmpeg） | — |
| **GPU 需求** | 无（CPU 渲染即可） | 有（HEYGEM 需要 GPU） | — |

### 2.2 是否应该分开处理？

**结论：应该分开，且当前代码已经正确分离。** 理由：

1. **技术栈完全不同**：scroll 是纯 CPU 的 PIL 渲染管线（`make_scroll_video.py`），avatar 依赖 GPU 容器（HEYGEM）做嘴型对齐。合并只会增加复杂度。
2. **目标用户群体不同**：
   - **scroll 面向**：高频量产型用户（每天 2-3 条口播科普，不需要露脸，追求效率）
   - **avatar 面向**：品牌信任型用户（需要真人数字人形象建立专业感，愿意等更长时间）
3. **字幕引擎的分工已经合理**：
   - scroll：字幕是**唯一视觉元素**（提词器式逐字高亮），需要精细控制字号/行数/位置/描边（P4 已实现）
   - avatar：字幕是**附加层**（烧在视频上），用标准 ASS 字幕轨即可

### 2.3 音频处理的统一性

两种模式的音频处理**应该统一且已经统一**：
- 共用同一套 CosyVoice voice_id（老张 zhangc2 / 江老师 jiangnv3）
- 共用同一套 EMOTION_PROSODY 情绪韵律映射表（6 类）
- 共用同一个 `qwen_tts.synth()` 调用入口
- avatar 模式的双声按性别选声线（P3 已实现）

**建议：不要拆分音频处理为独立模块。** 维护一套 TTS 管线比维护两套成本低得多。字幕参数（P4）仅影响 scroll 的渲染层，不影响音频。

## 三、智能选题模块精简评估

### 3.1 当前选题模块的数据流向

```
P5 智能选题 (topic.blade.php)
  ↓ AI 生成（DeepSeek /topic）
  ↓ "去二创"按钮 → sessionStorage 携带选题 JSON
智能二创 (rewrite.blade.php)
  ↓ 改写 + 违禁词清洗 (/rewrite)
  ↓ "去出片"按钮 → 自动推荐 mode(scroll/avatar) + 携带文本
视频出片 (scroll.blade.php)
```

**直接关联**：选题 → 二创 → 出片（强链路，不可断）

**无关联或弱关联**：

| 下游模块 | 与选题的关联强度 | 说明 |
|---|---|---|
| 形象克隆 | **无关联** | 克隆是独立流程，不依赖选题 |
| 声音克隆 | **无关联** | 同上 |
| 封面素材 | **无关联** | 封面按行业分类模板选择，不依赖具体选题 |
| 质检 | **间接关联** | 质检检查的是最终改写稿，不是原始选题 |
| 外发 | **间接关联** | 外发时才需要填标题/描述，可从选题继承也可手写 |
| 数据复盘 | **间接关联** | 复盘看的是发布后的播放数据，与选题内容无关 |

### 3.2 关于取消"行业必填维度"

用户提出取消左上部"行业（必填纬度）"及下方文本框。我的评估：

**支持取消的理由**：
1. 当前平台的实际场景是**财税垂直领域**（慧根堂税务风险咨询），所有选题天然属于财税行业，"行业"字段信息量为零
2. 选题的 AI 提示词中注入"行业=税务风险"比让用户每次手动选更高效
3. 减少一个必填字段降低新租户的使用门槛

**保留但降级的方案（折中）**：
- 将"行业"从**必填**改为**预填充默认值**（自动填"财税科普"，允许修改）
- 保留平台维度筛选中的"热度/钩子/形式"三个有实际区分度的筛选项
- 取消自由文本框（用户很少自定义行业名）

**关于目标平台范围（视频号/抖音/小红书）**：
- 这三个平台的选择在 UI 上已经是 `<select>` 固定选项，不含快手/B站
- 如果未来确实不会扩展到其他平台，当前实现已经足够精简
- **建议**：将平台选择从 `<select>` 改为三个 **toggle 按钮**（视觉更轻量，一键切换），同时移除"行业"必填

### 3.3 选题模块与其他模块的最小保留接口

即使精简后，选题仍需保留以下接口以确保链路不断：

```
选题 → 二创：sessionStorage / POST body 携带 {title, raw_content, topic_id}
二创 → 出片：POST body 携带 {dialogue, rewrite_mode, target_duration}
出片 → 外发：VideoJob.title / description 可从选题继承
```

这些接口都是**已有的**，精简选题 UI 不影响下游数据流。

## 四、差异化功能方案（3 个可行提案）

### 4.1 方案 A：公众号自动流水线（选题→出片→定时发送全闭环）

**痛点**：当前平台只管"出片"，不管"发到哪里、什么时候发"。用户出片后需手动下载视频→打开公众号后台→手动上传→手动填写文案→手动定时发布。每条视频重复 5+ 步操作。

**设计方案**：

```
新增模块：AutoPipeline（自动化流水线）
├── 内容计划表 content_plans
│   ├── tenant_id, title, topic_type, target_platform(wechat_mp)
│   ├── schedule_at (发布时间)
│   ├── status: draft → generating → reviewing → scheduled → published
│   ├── video_job_id (关联出片任务)
│   └── publish_record_id (关联外发记录)
│
├── 计划编排页 /studio/pipeline
│   ├── 日历视图（拖拽排期）
│   ├── 一键生成（批量选题→二创→出片）
│   └── 定时任务（Laravel Scheduler + queue worker）
│
└── 公众号 API 对接
    ├── access_token 缓存（Redis TTL 7200s）
    ├── 草稿箱 API（draft/add + draft/publish）
    └── 素材上传 API（cgi-bin/material/add_material）
```

**技术可行性**：✅ 高
- 微信公众号 API 成熟稳定（草稿箱/素材上传/群发接口均有官方文档）
- Laravel Scheduler 原生支持 cron 式定时任务
- Redis 已在 Docker 栈中运行，可直接缓存 access_token
- 出片产物已是 MP4，符合公众号视频要求（≤10MB / ≤10分钟 / MP4 H.264）

**差异化价值**：⭐⭐⭐⭐⭐
- 市面上几乎所有数字人 SaaS 都停在"出片即结束"
- 从选题到自动发布的**端到端自动化**是真正的竞争壁垒
- 特别适合财税这类需要**规律性日更**的垂类账号（每天固定时间发 1-2 条）

**开发量估算**：~3-4 天（含 API 对接 + 排期 UI + 异步队列 + 错误重试）

---

### 4.2 方案 B：朋友圈文案引擎（基于视频内容自动生成）

**痛点**：视频发出去了，但朋友圈的转发文案怎么写？大多数用户要么复制视频标题，要么随便写一句，错失了朋友圈私域流量转化的机会。

**设计方案**：

```
新增模块：MomentEngine（朋友圈文案引擎）
├── 输入：VideoJob ID（或出片完成的 dialogue 文本）
├── 处理流程：
│   ① 提取视频核心观点（DeepSeek 摘要）
│   ② 匹配钩子类型（留资/咨询/私域/认知）
│   ③ 按模板生成 3 版文案：
│      - A版：悬念提问型（"你公司有没有…？"）
│      - B版：数据冲击型（"XX%的企业都…"）
│      - C版：故事共鸣型（"上周有个客户…"）
│   ④ 用户选择/微调 → 一键复制
│
├── 文案模板库 moment_templates
│   ├── category: hook/question/story/data
│   ├── tone: professional/casual/urgent
│   ├── length: short(≤50字) / medium(≤100字) / long(≤200字)
│   └── variables: {{company_type}}, {{pain_point}}, {{stat}}
│
└── 输出：3 条候选文案 + 推荐理由
```

**技术可行性**：✅ 高
- 纯文本生成，调用 DeepSeek API 即可（已有 `/topic` 和 `/rewrite` 的 AI 调用先例）
- 模板变量替换用简单的字符串插值
- 无需对接任何第三方 API（微信朋友圈无法 API 发送，只能辅助生成文案）

**差异化价值**：⭐⭐⭐⭐
- 解决"出了视频不知道怎么发朋友圈"的实际痛点
- 文案模板可积累优化（根据用户选择率 A/B 测试最佳模板）
- 与视频出片形成**内容矩阵**（主视频 + 朋友圈引流文案 + 公众号长文）

**开发量估算**：~2 天（含模板设计 + AI prompt 调优 + 选择 UI）

---

### 4.3 方案 C：爆款复刻模板库（高互动率视频→一键复用全套参数）

**痛点**：某条视频爆了（7天互动率≥8%），用户想"再做一条类似的"，但忘了当时用的什么参数（字幕大小？语速？情绪标注？改写提示词？）。只能从头来过。

**设计方案**：

```
新增模块：HitClone（爆款复刻）
├── 触发入口：数据复盘看板中标记"爆款"的视频卡片
│   └── 一键"复刻此条"按钮
│
├── 复刻快照 hit_snapshots
│   ├── video_job_id (FK)
│   ├── snapshot JSON:
│   │   ├── dialogue (原始对话稿)
│   │   ├── rewrite_mode / preserve / target_duration
│   │   ├── subtitle_size / lines / outline / position
│   │   ├── emotion_annotations (情绪标注数组)
│   │   ├── ai_rewrite_prompt_hash (改写提示词版本)
│   │   ├── cover_asset_id
│   │   └── mode (scroll/avatar)
│   ├── engagement_score (互动率)
│   └── created_at
│
├── 复刻流程：
│   ① 加载快照 → 自动回填 scroll 页所有字段
│   ② 用户微调（改几个字/换封面/调时长）
│   ③ 提交出片 → 新 VideoJob 关联 parent_snapshot_id
│   ④ 追踪复刻效果 vs 原版的互动率对比
│
└── 爆款排行：
    ├── 按互动率排序的本租户历史视频
    ├── 标注"可复刻"标签（有完整快照的）
    └── 跨租户匿名爆款池（平台级，脱敏展示标题+互动率）
```

**技术可行性**：✅ 极高
- 快照就是序列化当前 VideoJob 的全部入参，零新技术
- `MetricDaily` 已有播放/互动数据，可直接算互动率
- 回填字段只需在前端 JS 做 `Object.assign(formData, snapshot)`

**差异化价值**：⭐⭐⭐⭐⭐
- **数据驱动的迭代能力**——把成功经验变成可复用的资产
- 跨租户爆款池（匿名脱敏）形成**社区效应**："看看别的财税账号什么内容爆了"
- 降低新租户冷启动难度（直接复刻平台验证过的爆款参数组合）

**开发量估算**：~2-3 天（快照存储 + 回填逻辑 + 排行 UI + 对比看板）

---

### 4.4 三个方案的优先级建议

| 方案 | 差异化程度 | 开发量 | 技术风险 | 建议优先级 |
|---|---|---|---|---|
| **A 公众号自动流水线** | ⭐⭐⭐⭐⭐ | 3-4 天 | 中（需微信 API 权限） | **P7 第一优先** |
| **B 朋友圈文案引擎** | ⭐⭐⭐⭐ | 2 天 | 低（纯 AI 文本） | **P7 第二优先** |
| **C 爆款复刻模板库** | ⭐⭐⭐⭐⭐ | 2-3 天 | 低（纯数据+UI） | **P7 第三优先** |

**推荐实施顺序**：C → B → A（先做低风险的爆款复刻快速见效，再做文案引擎增强内容矩阵，最后做公众号流水线打通全闭环）

## 五、架构科学性评估

### 5.1 当前架构的优点

| 维度 | 评价 | 说明 |
|---|---|---|
| **职责分离** | ✅ 好 | Laravel 管 Web/鉴权/数据，Python 8500 管 AI/渲染/TTS，HEYGEM 管嘴型。三层各司其职 |
| **混合云路线** | ✅ 合理 | Web 层可上云（轻量），渲染留在本地（GPU 依赖），经 frp 穿透。避免云服务器 GPU 成本 |
| **多租户模型** | ⚠️ 够用但不够严谨 | 手动 `where('tenant_id')` 隔离，无全局 Scope。功能正确但**防御性不足**——新增查询易遗漏 |
| **并发护栏** | ✅ 优秀 | 全局+单租户双重闸（3/2），硬超时+进程树清理。生产级健壮性 |
| **错误处理** | ✅ 合格 | 422/429/402/419 各场景有专门响应，前端 JSON 防护已加 |
| **缓存策略** | ⚠️ 需注意 | opcache 铁律已文档化但依赖人工执行（docker restart）；Blade 编译缓存有 view:clear |

### 5.2 架构缺陷与改进建议

#### 缺陷 1：无全局租户作用域（高危）

**现状**：每个控制器方法内手动写 `->where('tenant_id', $this->tenantId())`。11 个控制器 × 平均 3-5 个查询 = **30-55 个隔离点**，任一新增查询遗漏 = 越权读取。

**改进方案**：
```php
// app/Models/TenantScope trait（或全局 Eloquent Scope）
class Tenant extends Model {
    protected static function booted() {
        static::addGlobalScope('tenant', function ($builder) {
            if (auth()->check() && auth()->user()->tenant_id) {
                $builder->where('tenant_id', auth()->user()->tenant_id);
            }
        });
    }
}
// 所有业务模型 use HasTenant; → 自动隔离，无需手动 where
```
**优先级**：🔴 高（安全底线）

#### 缺陷 2：同步队列阻塞（性能瓶颈）

**现状**：`.env` `QUEUE_CONNECTION=sync`，所有 8500 调用（选题/二创/质检/出片）都是**同步 HTTP 代理**。出片耗时 5-15 分钟期间 PHP-FPM 进程被占用。

**改进方案**：
```php
// 改用 database 队列 + Laravel Queue Worker
VideoController::generate() {
    $job = RenderVideoJob::dispatch($payload);
    // 立即返回 job ID，前端轮询 /status/{id}
}
// docker-compose.yml 加一个 queue worker 容器
// queue: command: ["php", "artisan", "queue:work", "--sleep=3", "--tries=3"]
```
**优先级**：🟡 中（当前单租户够用，多租户并发时必改）

#### 缺陷 3：8500 单点故障无降级

**现状**：Laravel 经 `host.docker.internal:8500` 直连 Python 微服务。8500 挂了 = 所有 AI/渲染功能全挂。

**改进方案**：
```php
// PipelineService with circuit breaker
class PipelineService {
    const THRESHOLD_FAILURES = 3;
    const COOLDOWN_SECONDS = 60;

    public function call($endpoint, $data) {
        if ($this->isCircuitOpen()) {
            throw new ServiceUnavailableException('8500 服务暂不可用');
        }
        // 正常调用 + 失败计数 + 自动恢复
    }
}
```
**优先级**：🟢 低（8500 是 NSSM 常驻服务，崩溃自启；但加上更稳健）

#### 缺陷 4：无 API 版本化

**现状**：只有 web 路由（routes/web.php），无 api.php。8500 的 REST 接口也没有版本前缀。

**改进方案**：如果未来要开放 API 给第三方（如飞书/企微机器人触发出片），需加 `routes/api.php` + `api/v1/` 前缀 + Token 认证。
**优先级**：⚪ 暂不需（当前仅 Web UI 使用）
